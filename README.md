# RAG over Postgres + pgvector

A document Q&A system where **Postgres is the only piece of infrastructure**:
it stores relational metadata (documents, authors, tags), full-text search
indexes, and vector embeddings — all in one database, queried with one SQL
engine. Retrieval combines classic keyword search with semantic vector
search using Reciprocal Rank Fusion, and the final answer is generated by
Claude, grounded in the retrieved text with citations.

## Why this project (and not just another vector-DB demo)

Most "RAG tutorial" projects reach for a dedicated vector database
(Pinecone, Chroma, Weaviate...) and treat it as a black box. This project
deliberately keeps everything in Postgres to show:

- Relational schema design (documents ↔ chunks, foreign keys, generated
  columns, arrays for tags)
- Two different index types (`HNSW` for vectors, `GIN` for full text) and
  when each one matters
- Hybrid search: pure vector search misses exact keywords/codes/names;
  pure keyword search misses paraphrases. This merges both with
  [Reciprocal Rank Fusion](https://en.wikipedia.org/wiki/Learning_to_rank#Reciprocal_rank_fusion)
  rather than picking one.
- Metadata filtering pushed down into SQL (`WHERE d.author = ...`) instead
  of filtered in Python after the fact — so Postgres's indexes actually get
  used.

## Architecture

```
                     ┌─────────────────────┐
   files (.txt/.pdf) │                     │
   ─────────────────▶│   ingest.py         │
                      │  chunk → embed      │
                      └─────────┬───────────┘
                                │ INSERT
                                ▼
                  ┌───────────────────────────────┐
                  │           Postgres            │
                  │  documents (metadata)         │
                  │  chunks (text + VECTOR(384)   │
                  │          + tsvector)          │
                  │  HNSW index │ GIN index        │
                  └───────────────┬────────────────┘
                                  │ SELECT (2 queries)
                                  ▼
                     ┌─────────────────────────┐
   question  ───────▶│  retrieval.py           │
                      │  vector search  ┐       │
                      │  full-text search┴─ RRF │
                      └───────────┬─────────────┘
                                  │ top-k chunks
                                  ▼
                     ┌─────────────────────────┐
                     │  generate.py             │
                     │  build cited prompt →   │
                     │  Claude API              │
                     └───────────┬─────────────┘
                                 ▼
                              answer
```

## Setup

### 1. Start Postgres with pgvector

```bash
docker compose up -d
```

This pulls the `pgvector/pgvector:pg16` image and automatically runs
`init-db/01_schema.sql` on first boot (creates the extension, tables, and
indexes).

### 2. Install Python dependencies

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 3. Configure environment variables

```bash
cp .env.example .env
```

Edit `.env` and add your `GROQ_API_KEY` (get one at
console.anthropic.com). This is only needed for the final answer-generation
step — ingestion and retrieval work without it.

### 4. Ingest the sample documents

```bash
python3 -m src.cli ingest --path data/sample_docs
```

Add your own files just by pointing `--path` at any `.txt`, `.md`, or
`.pdf` file or folder:

```bash
python3 -m src.cli ingest --path data/sample_docs/pgvector_overview.txt --author "Jane Doe" --tags research postgres
```

### 5. Ask questions

```bash
python3 -m src.cli ask "What's the difference between HNSW and IVFFlat?"
python3 -m src.cli ask "Why combine vector search with full text search?"
python3 -m src.cli ask "What does Jane Doe's document say?" --author "Jane Doe"
```

Each answer prints the ranked table of retrieved chunks (with both the
vector rank and full-text rank, and the fused RRF score) before the
generated answer, so you can see exactly what fed into the prompt.

## Project layout

```
rag-postgres-pgvector/
├── docker-compose.yml       # Postgres + pgvector container
├── init-db/01_schema.sql    # Tables, indexes, extension setup
├── src/
│   ├── config.py            # Env var loading
│   ├── db.py                # psycopg2 connection + pgvector adapter
│   ├── embeddings.py        # sentence-transformers wrapper
│   ├── chunking.py          # sliding-window text chunker
│   ├── ingest.py            # file → chunks → embeddings → INSERT
│   ├── retrieval.py         # vector search + full-text search + RRF
│   ├── generate.py          # builds grounded prompt, calls Claude
│   └── cli.py                # `ingest` and `ask` commands
├── data/sample_docs/        # demo .txt files
├── tests/test_chunking.py
└── requirements.txt
```

## Extending this project

Some natural next steps if you want to go further (and good talking points
in an interview):

- **Evaluation harness**: build a small set of (question, expected
  document) pairs and measure retrieval precision/recall — turns "it works
  on my demo" into a defensible number.
- **IVFFlat vs HNSW benchmark**: load a much bigger dataset (e.g. Wikipedia
  abstracts) and compare index build time and query latency between the
  two pgvector index types — this is exactly the kind of tradeoff analysis
  a DBA/data-engineer interview loves.
- **Row-level security**: add multi-tenant access control so different
  users only see their own documents, using Postgres RLS policies instead
  of filtering in application code.
- **Streaming ingestion**: hook up Postgres logical replication or a
  simple polling job so newly added rows in an existing operational table
  get embedded automatically (a lightweight CDC pattern).
- **Swap the embedding model**: try a larger model and re-run the same
  queries to see how retrieval quality changes — remember to update
  `VECTOR(384)` in the schema to match the new dimension.

## What this demonstrates (for your CV / interview prep)

- Relational schema design with foreign keys, generated columns, arrays
- Two Postgres index types and when to use each (`HNSW`, `GIN`)
- Writing and reading `EXPLAIN ANALYZE` output to reason about query plans
- Hybrid search design (a real, current pattern in production RAG systems)
- Parameterized SQL (no string-formatted queries — injection-safe)
- Clean separation of ingestion, retrieval, and generation as independent,
  testable stages
